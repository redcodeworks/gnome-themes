# gnome-themes

Colour schemes for GNOME, one directory per scheme (so far: `gruvbox-material`). The approach is
the same for every theme: **keep the stock theme and change only colours.**

| Part | Read by | How it is made |
|---|---|---|
| `themes/<Name>/gtk-3.0/` | GTK3 apps | generated by `tools/gtk3-theme-gen.py` from GTK 3's own built-in Adwaita stylesheet; only colour values change. |
| `themes/<Name>/gtk-4.0/` | **plain GTK4 apps without libadwaita** (pavucontrol, gtkmm/GTK4 programs) | generated by `tools/gtk4-theme-gen.py` from GTK 4's built-in `Default-light.css`/`Default-dark.css`; only colour values change (relative-colour functions such as `rgb(from X r g b / calc(alpha * .4))` keep their syntax, only the origin colour is recoloured). |
| `libadwaita/gtk.css` | **libadwaita apps** (Nautilus, Settings, ...) | hand-written override of libadwaita's named colours. libadwaita ignores the GTK theme and reads only the user stylesheet `~/.config/gtk-4.0/gtk.css`, so this is a user-level file, not part of the theme folder. |

Both generators share one engine, `tools/themegen.py`; the scheme's `palette.toml` is the only
input (greys ramp, accent families, exact overrides). GTK 4.24's greys and blue/red/orange anchors
equal GTK3's, so no separate `[gtk4]` section is needed; GTK4-only stock colours (the `#26a269`
success green, ...) are `exact` entries.

Layout: `<scheme>/palette.toml`, `<scheme>/themes/<InstalledName>/…`, `<scheme>/libadwaita/gtk.css`.
Everything under `themes/` is installed as-is; `libadwaita/` is installed by `just install-user`.

```
just list
just generate gruvbox-material                      # needs python3-gobject + GTK 3 and GTK 4
just install gruvbox-material                       # themes to /usr/share/themes (root)
just install gruvbox-material ~/.themes             # per user; real copies (Flatpaks cannot follow symlinks)
just install-user gruvbox-material                  # libadwaita/gtk.css -> ~/.config/gtk-4.0/gtk.css
```

`just install-user` never overwrites a different `~/.config/gtk-4.0/gtk.css`: it stops and tells you
to diff, and only `just install-user gruvbox-material force` replaces it (keeping a `.bak`). If that
file is generated by something else (e.g. a script that appends structural CSS), merge by hand.

Flatpak apps only see themes under `~/.themes` (give them `--filesystem=~/.themes:ro`, and
`xdg-config/gtk-4.0:ro` for the libadwaita file), not the host's `/usr/share/themes`.

Which variant is used: GTK3 picks `gtk.css` (light) or `gtk-dark.css` (dark) from
`gtk-application-prefer-dark-theme` in `~/.config/gtk-3.0/settings.ini`, not from `color-scheme`.
GTK 4.24 uses `gtk-dark.css` when the colour scheme is dark (the portal/dconf `color-scheme`, which
also sets `gtk-interface-color-scheme`) or `gtk-application-prefer-dark-theme` is true.
Host and Flatpak runtime (GNOME 51) ship the same GTK 4.24.1 `Default-*.css` (identical hashes), so
one generated copy serves both.

Proof that only colours changed: mask hex colours, `rgb()/rgba()` and `white`/`black` in the stock
extract and in the generated file (minus its header comment) and compare line by line; they are
identical, and `Gtk.CssProvider` reports 0 parse errors for both files.
