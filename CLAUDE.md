# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Terminal-inspired colour schemes for GNOME (GTK 3, GTK 4/libadwaita, GNOME Shell) plus an installer for the themes and for icon sets. A theme is a top-level directory (`gruvbox-material`, `nordic`, `dracula`, `catppuccin`, ...). Each theme takes the *stock* stylesheet unchanged and replaces **colour values only**; selectors, geometry and assets stay stock. The one deliberate addition is a single marked calendar override block at the end of every generated Shell stylesheet. `README.md` is the user-facing documentation; `AGENTS.md` is a notice aimed at outside agents.

## Commands

Public recipes (ten, all thin calls into `tools/themectl.sh`; run from the repo root): `list-themes`, `install-themes [scheme]`, `update-themes`, `remove-themes [scheme]`, `switch-theme [scheme] [accent]`, and the same five for icons (`*-icons`, `switch-icons`). Without a name, install/remove/switch show a checklist (SPACE ticks, ENTER confirms, q cancels). `THEMES_DEST`, `ICONS_DEST`, `ICON_SOURCES`, `ICONS_URL`, `GNOME_THEMES_CACHE` and `FORCE=1` redirect or override the installer, which is how tests stay out of the real home.

Development (private recipes; need python3-gobject, GTK 3, GTK 4 and gnome-shell installed):
- `just generate [scheme|all]` regenerates everything for a scheme (palette, GTK3/GTK4/Shell themes, libadwaita file, accent maps). Generated files are committed; never hand-edit them.
- `just test <scheme>` or `python3 -I tools/selftest.py <scheme> [contrast|gtk3|gtk4|shell|all]` runs the checks for one scheme.
- `just new-scheme <scheme-dir> <ptyxis-palette> [light-palette]` starts a new scheme: `tools/scheme-from-ptyxis.py` writes a DRAFT `scheme.toml` from a Ptyxis built-in palette (`tools/ptyxis-palette.sh list|show <name>`, `PTYXIS_BIN` overrides the binary; names are UTF-8, e.g. Rosé Pine, the helper reads the binary as 8-bit strings) and prints the TODO decisions (including `ptyxis`: run `python3 -I tools/ptyxis-compare.py <scheme-dir>` to see whether a built-in qualifies); then the normal pipeline. Private recipes still run by name (`just --justfile <file> new-scheme ...`, which is how the image's `ujust gnome-themes new-scheme` reaches them). The walk-through is the project skill `.claude/skills/build-scheme/SKILL.md`.
- `tools/test.sh [--rebuild] [scheme ...]` is the whole suite, an OPTIONAL developer tool: **CI on the pull request is the test**, and the local full run is not used (not by agents either; run only quick checks that fit a change: `tools/selftest.py` for the scheme, `tools/ptyxis-compare.py --check`, `bash -n`, shellcheck). It covers (lint, hygiene, regeneration, selftest per scheme, install/switch/update/remove for every scheme and accent, icon recipes). It builds a cached Fedora 45 image from `tools/test.Containerfile` + `tools/test-packages.txt` and runs itself in a throwaway podman/docker container with the repo mounted read-only. It tests the **committed HEAD** (a fresh clone), so commit before running it. The first full run of a change is therefore the CI run on its pull request.

## Principle: official source first, then the Ptyxis built-in, invented last

A variant's colours come from, in this order: (1) an OFFICIAL source (the scheme's own repo, tmTheme or palette file, project terminal ports; verified against the raw file and recorded in the `scheme.toml` header), (2) the Ptyxis built-in palette of the same name (`tools/ptyxis-palette.sh show <name>`), (3) invented or derived values, marked as such. Each variant says which in `[<variant>.terminal]`: `source = "official: <repo/url, date verified>"` with `builtin_differs = { name = "<built-in>", de = <max delta E over the 18 colours>, note = "<why official wins>" }`, or `source = "<built-in name>"` (then `bg_deep`/`fg` are its Background and Foreground, the six accents its Color1-6, and the table holds its real black, white and brights), or `no_builtin = "<why>"` (no built-in exists for that variant; own values stay). Where there is no official source, a difference from the same-named built-in means the scheme is wrong, not the built-in. A built-in split by mode gives each variant its own palette (Rosé Pine / Rosé Pine Dawn); a sectioned one gives its [Light] and [Dark]. A scheme that differs from its built-in cannot use it: it declares `ptyxis = "generated"` and the generated palette carries the official colours. A colour may differ from its source only as a **nudge**, forced by a contrast check (`tools/selftest.py`, e.g. fg on the window under 4.5:1) and listed in `[<variant>.nudge]` as `Key = { from, to, de, why }` with at most NUDGE_MAX delta E (one constant in `tools/ptyxis-compare.py`). `ptyxis-compare.py --check` fails on a missing source, an unlisted difference from a built-in source, a stale or oversized nudge, or an official source without a correct `builtin_differs`. Nordic (dark only) uses the sectioned Nord built-in on purpose (`ptyxis_light_section_accepted = true` in its scheme.toml): under a light system colour scheme Ptyxis shows Nord's [Light] section while the rest of Nordic stays dark.

## Architecture

**Generation pipeline** (needs several files to see): `<scheme>/scheme.toml` (roles per variant, the six terminal ANSI accents, optional seventh `orange`, `default_accent`) -> `tools/palette-from-scheme.py` derives `<scheme>/palette.toml` (ramps, colour families, exact overrides; the fixed derivation rules are documented in its header) -> `tools/gtk3-theme-gen.py`, `gtk4-theme-gen.py` and `shell-theme-gen.py` read the **stock** CSS from the installed libraries (GTK3 Adwaita and GTK4 Default resources, `gnome-shell-theme.gresource`) and replace colour tokens through the shared engine `tools/themegen.py` -> `<scheme>/themes/<Name>/...`; `tools/libadwaita-gen.py` writes `<scheme>/libadwaita/gtk.css`; `tools/ptyxis-gen.py` writes the Ptyxis palette `<scheme>/ptyxis/gnome-themes-<scheme>.palette` straight from `scheme.toml`, **only for schemes that declare `ptyxis = "generated"`** (every scheme declares `ptyxis = "<Ptyxis built-in name>"` or `"generated"` plus `ptyxis_reason`; a scheme on a built-in has no palette file, and the generator removes a stale one; `tools/ptyxis-compare.py` compares the schemes with the built-ins, holds the single close-match THRESHOLD, NUDGE_MAX and the qualification rules in its header, and `--check` verifies the declarations, the sources and the listed nudges; rules of the generated format in `ptyxis-gen.py`'s header; optional `[<variant>.terminal]` tables hold real blacks/brights with their source; shared helpers in `tools/schemeroles.py`); `tools/gtksourceview-gen.py` writes the GtkSourceView 5 style schemes `<scheme>/gtksourceview/gnome-themes-<scheme>-{dark,light}.xml` (contrast rule and role mapping in its header). The stock files are recoloured in place because `@define-color` overrides do nothing visible in GTK 3.24 (colours are inlined) and St has no such feature.

**Structure guarantee**: `tools/selftest.py` masks colour tokens in the stock file and the generated file and requires 0 differing lines (the calendar override block is stripped first and checked separately). Stock drift in a newer Fedora therefore fails the regeneration check: run `just generate <scheme>` and commit.

**Accents**: `tools/accent-maps-gen.py` re-runs the recolour per accent, diffs token by token and writes `<scheme>/accents/<accent>.{dark,light}.sed` plus `accents/list`. The maps are two-phase sed scripts (token -> placeholder -> new token) and are verified against the directly generated files. Some `accent_fg` / orange role values are nudged by a few units so every sed key token stays unique (the generated `palette.toml` header says which). Dark-only schemes fill the GTK light slot from the dark palette and have no Shell-Light folder.

**Installer** (`tools/themectl.sh`, one script, `themes` and `icons` kinds): themes copy from the checkout (`update-themes` does `git fetch` + `pull --ff-only` first); icon sets come from the sources in `tools/icon-sources.conf` (`top`, `root` and `script` layouts; Tela and Fluent run their upstream `install.sh` into a temp dir). The registry DECLARES every set name (column 4: `top` = directories, `dir=SetName` when the installed name differs; `root` = the name; `script` = variants), so listing, the install checklist, switch and remove need no clone and no network; a source is cloned (shallow, under `~/.cache/gnome-themes/icons/<source>`) only after the choice, for the sources of the chosen sets (update: of the installed sets), and a failed clone skips just that source. After a clone `verify_source` warns once per mismatch (`registry says X, upstream has no X` / `upstream has Y not in the registry`) and carries on; when an upstream renames or adds a set, fix the registry. Each set's own folder is replaced wholesale, never the whole destination. Installed folders carry a `.gnome-themes` marker; a same-named folder without it (for example a third-party `Dracula`) is only replaced after a `y` at the prompt (or `FORCE=1`). A generated Ptyxis palette is a marked single file in `PTYXIS_PALETTES` (same collision guard; install/update/remove copy, refresh, delete it); a scheme that declares a built-in installs and removes nothing. `switch-theme` sets the dconf `palette` key (the generated palette's Name or the built-in's name, printed) of the default profile and of profiles that already have one (`pty_builtin` in `themectl.sh` reads the declaration). GtkSource style schemes are installed like the palette (marker comment, same guard) into the user styles dir and the data dirs of installed Flatpak editors (they ignore host `~/.local/share`); `switch-theme` sets the `/org/gnome/TextEditor/style-scheme` dconf key (and Builder's only when it exists). Flatpak access is managed here too (`fp_*` in `tools/themectl.sh`): after `switch-theme` it offers (prompt, default no; no terminal: prints the command) the missing global read-only entries of one list, records only what it added in `$XDG_STATE_HOME/gnome-themes/flatpak-overrides`, and after the last theme and icon set (marker files) is removed it offers to undo exactly the recorded entries; never silent, no new recipe. `switch-theme` applies the accent (sed maps over the installed copies, remembered in `$XDG_STATE_HOME/gnome-themes/accents`), sets the GTK and Shell themes (dconf fallback when gsettings lacks the User Themes schema) and the libadwaita file `~/.config/gtk-4.0/gtk.css` (replaced silently only if generated by gnome-themes or a `.bak` exists, otherwise it asks).

## Workflow

`main` is protected: work goes to `testing`, CI (`.github/workflows/ci.yml`: job `test` runs `tools/test.sh` in a Fedora 45 container, job `secrets` runs gitleaks) must pass, and a pull request `testing` -> `main` is then merged (see README, Contributing). CI shellcheck runs at warning level.

## Reference moved from the README

The README is user-facing and short; these details live here.

- **Schemes and notes**: gruvbox-material, nordic, dracula, catppuccin, tokyo-night, solarized, everforest, fairy-floss, material, monokai, rose-pine, sweet, aubergine (Ubuntu terminal look). Dark-only: nordic, fairy-floss, monokai, sweet, aubergine. `fairy-floss` has no upstream licence and partly invented surfaces; `monokai` is classic Monokai, not Monokai Pro; light Gruvbox Material and Material have no built-in (`no_builtin`) and keep their own values. Where the official palette differs from the built-in, `builtin_differs` records distance and reason and the scheme generates its own Ptyxis palette.
- **Shell calendar override**: the Shell themes are stock + colours + one marked block drawing the calendar flat (no circle per day, plain weekday headings, month label and arrows).
- **Accents**: one of the six terminal colours plus orange where the scheme has one (`<scheme>/accents/list`; not `rose-pine` and `fairy-floss`, whose upstream has no orange). Sed maps live in `accents/<accent>.{dark,light}.sed`; the chosen accent is remembered in `~/.local/state/gnome-themes/accents`. GTK 3 follows `gtk-application-prefer-dark-theme` in `~/.config/gtk-3.0/settings.ini`, not `color-scheme`.
- **Ptyxis**: a scheme uses a built-in only when every colour is within the close-match distance of it (`tools/ptyxis-compare.py`, one THRESHOLD) and it follows light/dark like the scheme (Ptyxis keeps one palette name per profile, so two flat built-ins such as Catppuccin Latte and Mocha cannot stand in for a light/dark pair; the generated pair carries exactly their colours plus listed nudges). Generated palettes show in Ptyxis as "<Title> (GNOME Themes)", live in `~/.local/share/org.gnome.Ptyxis/palettes` (`PTYXIS_PALETTES` overrides), follow the folder marker and collision rules; built-ins are never copied or removed. `switch-theme` sets the palette on the default profile and on every profile that already has one (via `dconf`; with no profile it says so and skips) and prints the choice; the accent does not change it.
- **GtkSourceView**: installed into `~/.local/share/gtksourceview-5/styles` and, because Flatpak editors only read their own data dir, into `~/.var/app/org.gnome.TextEditor|org.gnome.Builder/data/gtksourceview-5/styles` when installed (no sandbox permission needed). `switch-theme` sets Text Editor's `style-scheme` (-dark while the desktop is dark, else -light) and Builder's only if present. Syntax colours are held at 4.5:1 on the editor background (comments 3:1) by changing lightness only; the generated file lists what moved.
- **Installer details**: checklist keys: SPACE, ENTER, q, up/down or j/k, a (all), n (none). `ICONS_URL` overrides the papirus source; icons use the XDG path (GTK also reads legacy `~/.icons`). Themes are real copies because Flatpak apps see `~/.themes`, not `/usr/share/themes`, and cannot follow symlinks. `update-themes` runs `git fetch` + `pull --ff-only` (quiet on a detached HEAD); icon clones under `~/.cache/gnome-themes/icons/<source>` are made or refreshed only for the sources of the sets being installed or updated (offline it uses the cache). Only each set's own folder is replaced. A same-named folder without the `.gnome-themes` marker is replaced or removed only after `y` (default no; no terminal: skipped with a message; `FORCE=1` overrides); folders from before the marker are adopted when their `index.theme` is identical. Tela and Fluent run their upstream `install.sh` (third-party code) into a temp dir. Icon sources: Papirus, Gruvbox Plus, Zafiro, candy, Tela, Fluent.
- **Flatpak access**: after `switch-theme`, if `flatpak` is installed and the global user override lacks any of `xdg-config/gtk-3.0:ro`, `xdg-config/gtk-4.0:ro`, `xdg-data/icons:ro`, `~/.themes:ro`, it asks once (default no); without a terminal it prints the exact `flatpak override --user --filesystem=...` command. Only missing entries are granted and recorded in `~/.local/state/gnome-themes/flatpak-overrides`; pre-existing entries are never recorded or removed. Removing the last theme and icon set asks (default no; no terminal: prints the `--nofilesystem` commands) to remove exactly the recorded entries.
- **New scheme**: `just new-scheme <dir> "<Ptyxis palette name>"` (see `tools/ptyxis-palette.sh list`), then `just generate <dir>`; checklist in `.claude/skills/build-scheme/SKILL.md`.
- **Requirements**: install needs `just`, bash and git; `just generate` needs python3, python3-gobject, GTK 3, GTK 4 and gnome-shell.
- **Testing and CI**: CI on the pull request is the test (job `test` runs `tools/test.sh` in a Fedora 45 container, job `secrets` runs gitleaks; both must pass to merge). Local tools (`tools/test.sh`, selftest, `ptyxis-compare.py --check`) are optional developer tools.
- **Licence**: tooling and docs MIT (`LICENSE`); generated theme files derive from stock GTK/GNOME Shell stylesheets and stay LGPL, each `*/themes/<Name>/` has its own `LICENSE`; `NOTICE` has the split and credits.

## Scope and delegation

- This repo is its own Claude project: work only inside it. Never edit anything outside it (other repos, the real themes or icons directories, home-directory configs, live gsettings/dconf). Tests use temp dirs and `THEMES_DEST` / `ICONS_DEST`, as `tools/test.sh` does when it is used.
- Anything that needs the outside (applying a theme on the desktop, a live check in the running Shell, a change in another repo) is not done here. Report it as a request under `Needs from hub:` to whoever spawned the session, who handles or delegates it.
- Work on this repo from other sessions goes through a project agent spawned by that hub, not through direct edits to these files.

Licences: tooling and docs MIT (`LICENSE`); each `*/themes/<Name>/` folder carries its own LGPL `LICENSE` because the generated CSS derives from GTK / GNOME Shell stock stylesheets. A new scheme needs its palette credit in `NOTICE`, provenance notes in `scheme.toml`, and the folder `LICENSE` (`just generate` copies it).
