# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Terminal-inspired colour schemes for GNOME (GTK 3, GTK 4/libadwaita, GNOME Shell) plus an installer for the themes and for icon sets. A theme is a top-level directory (`gruvbox-material`, `nordic`, `dracula`, `catppuccin`, ...). Each theme takes the *stock* stylesheet unchanged and replaces **colour values only**; selectors, geometry and assets stay stock. The one deliberate addition is a single marked calendar override block at the end of every generated Shell stylesheet. `README.md` is the user-facing documentation; `AGENTS.md` is a notice aimed at outside agents.

## Commands

Public recipes (ten, all thin calls into `tools/themectl.sh`; run from the repo root): `list-themes`, `install-theme [scheme]`, `update-theme`, `remove-theme [scheme]`, `switch-theme [scheme] [accent]`, and the same five for icons (`*-icons`, `switch-icon`). Without a name, install/remove/switch show a checklist (SPACE ticks, ENTER confirms, q cancels). `THEMES_DEST`, `ICONS_DEST`, `ICON_SOURCES`, `ICONS_URL`, `GNOME_THEMES_CACHE` and `FORCE=1` redirect or override the installer, which is how tests stay out of the real home.

Development (private recipes; need python3-gobject, GTK 3, GTK 4 and gnome-shell installed):
- `just generate [scheme|all]` regenerates everything for a scheme (GTK3/GTK4/Shell themes, libadwaita file, accent maps). Generated files are committed; never hand-edit them.
- `just test <scheme>` or `python3 -I tools/selftest.py <scheme> [contrast|gtk3|gtk4|shell|all]` runs the checks for one scheme.
- `just new-scheme <scheme-dir> <ptyxis-palette> [light-palette]` starts a new scheme: `tools/scheme-from-ptyxis.py` writes a DRAFT `scheme.toml` from a Ptyxis built-in palette (`tools/ptyxis-palette.sh list|show <id>`, ids are case-sensitive and UTF-8 (e.g. Rosé Pine), `PTYXIS_BIN` overrides the binary) and prints the TODO decisions (`ptyxis` is already the id; `python3 -I tools/ptyxis-compare.py <scheme-dir>` shows the distance to the candidates); then the normal pipeline. Private recipes still run by name (`just --justfile <file> new-scheme ...`, which is how the image's `ujust gnome-themes new-scheme` reaches them). The walk-through is the project skill `.claude/skills/build-scheme/SKILL.md`.
- `tools/test.sh [--rebuild] [scheme ...]` is the whole suite, an OPTIONAL developer tool: **CI on the pull request is the test**, and the local full run is not used (not by agents either; run only quick checks that fit a change: `tools/selftest.py` for the scheme, `tools/ptyxis-compare.py --check`, `bash -n`, shellcheck). It covers (lint, hygiene, regeneration, selftest per scheme, install/switch/update/remove for every scheme and accent, icon recipes). It builds a cached Fedora 45 image from `tools/test.Containerfile` + `tools/test-packages.txt` and runs itself in a throwaway podman/docker container with the repo mounted read-only. It tests the **committed HEAD** (a fresh clone), so commit before running it. The first full run of a change is therefore the CI run on its pull request.

## Principle: the Ptyxis built-in (by id) is the source of truth

For every scheme variant that has a Ptyxis built-in palette, the built-in decides the colours: `bg_deep` and `fg` are its Background and Foreground, the six `[<variant>.ansi]` accents its Color1-6, and its real black, white and brights (Color0, 7, 8-15) sit in `[<variant>.terminal]`; the terminal then shows exactly what the toolkit themes use. Roles that equalled an accent follow it; derived ladder roles (bg, surface, surface_high, fg_dim, comment) keep the fixed rules and are dropped from the explicit table where a changed background or foreground would make the ordering collide. Each variant says `source = "<built-in id>"` (the id it declares: `ptyxis`, or `ptyxis_light` for a flat light built-in) or `no_builtin = "<why>"` (Gruvbox Material light, Material light: the own values stay and the dark built-in serves both modes). There is no "official source" override and no `builtin_differs` any more, and no generated palette. A colour may differ from the built-in only as a **nudge**, forced by a contrast check of the GTK colours (`tools/selftest.py`: fg on window and view at 4.5:1) and listed in `[<variant>.nudge]` as `Key = { from = "<built-in value>", to, de, why }` with at most NUDGE_MAX delta E (one constant in `tools/ptyxis-compare.py`); today Solarized dark and light and Tokyo Night Day carry an `fg` nudge. The terminal itself always shows the built-in unchanged. `ptyxis-compare.py --check` fails on a missing id, a source that is not the declared id, an unlisted difference from the built-in, or a stale or oversized nudge. Nordic (dark only) uses the sectioned `nord` built-in on purpose (`ptyxis_light_section_accepted = true`): under a light system colour scheme Ptyxis shows Nord's [Light] section while the rest of Nordic stays dark. Provenance and credit notes in the `scheme.toml` headers and `NOTICE` say that the colours are taken from Ptyxis's palette of that name (mostly Gogh ports, per each built-in's header) and credit the project that inspired the theme.

## Architecture

**Generation pipeline** (needs several files to see): `<scheme>/scheme.toml` (roles per variant, the six terminal ANSI accents, optional seventh `orange`, `default_accent`) -> `tools/palette-from-scheme.py` derives `<scheme>/palette.toml` (ramps, colour families, exact overrides; the fixed derivation rules are documented in its header) -> `tools/gtk3-theme-gen.py`, `gtk4-theme-gen.py` and `shell-theme-gen.py` read the **stock** CSS from the installed libraries (GTK3 Adwaita and GTK4 Default resources, `gnome-shell-theme.gresource`) and replace colour tokens through the shared engine `tools/themegen.py` -> `<scheme>/themes/<Name>/...`; `tools/libadwaita-gen.py` writes `<scheme>/libadwaita/gtk.css`; `tools/ptyxis-compare.py` checks the Ptyxis declarations (`ptyxis = "<id>"`, optional `ptyxis_light = "<id>"`: Ptyxis BUILT-IN palette ids, nothing is generated for the terminal; see the Ptyxis bullet below; optional `[<variant>.terminal]` tables hold real blacks/brights with their source; shared helpers in `tools/schemeroles.py`); `tools/gtksourceview-gen.py` writes the GtkSourceView 5 style schemes `<scheme>/gtksourceview/gnome-themes-<scheme>-{dark,light}.xml` (contrast rule and role mapping in its header). The stock files are recoloured in place because `@define-color` overrides do nothing visible in GTK 3.24 (colours are inlined) and St has no such feature.

**Structure guarantee**: `tools/selftest.py` masks colour tokens in the stock file and the generated file and requires 0 differing lines (the calendar override block is stripped first and checked separately). Stock drift in a newer Fedora therefore fails the regeneration check: run `just generate <scheme>` and commit.

**Accents**: `tools/accent-maps-gen.py` re-runs the recolour per accent, diffs token by token and writes `<scheme>/accents/<accent>.{dark,light}.sed` plus `accents/list`. The maps are two-phase sed scripts (token -> placeholder -> new token) and are verified against the directly generated files. Some `accent_fg` / orange role values are nudged by a few units so every sed key token stays unique (the generated `palette.toml` header says which). Dark-only schemes fill the GTK light slot from the dark palette and have no Shell-Light folder.

**Installer** (`tools/themectl.sh`, one script, `themes` and `icons` kinds): themes copy from the checkout (`update-theme` does `git fetch` + `pull --ff-only` first); icon sets come from the sources in `tools/icon-sources.conf` (`top`, `root` and `script` layouts; Tela and Fluent run their upstream `install.sh` into a temp dir). The registry DECLARES every set name (column 4: `top` = directories, `dir=SetName` when the installed name differs; `root` = the name; `script` = variants), so listing, the install checklist, switch and remove need no clone and no network; a source is cloned (shallow, under `~/.cache/gnome-themes/icons/<source>`) only after the choice, for the sources of the chosen sets (update: of the installed sets), and a failed clone skips just that source. After a clone `verify_source` warns once per mismatch (`registry says X, upstream has no X` / `upstream has Y not in the registry`) and carries on; when an upstream renames or adds a set, fix the registry. Each set's own folder is replaced wholesale, never the whole destination. Installed folders carry a `.gnome-themes` marker; a same-named folder without it (for example a third-party `Dracula`) is only replaced after a `y` at the prompt (or `FORCE=1`). Ptyxis palettes are never installed (built-ins only); install, update, switch and remove delete leftover generated palette files of earlier versions from `PTYXIS_PALETTES`, only files that carry the marker line `# gnome-themes: <scheme>`, one output line per file (an unmarked file such as a hand-made palette is never touched). `switch-theme` writes the palette ID to the dconf `palette` key of the default profile and of profiles that already have one (`ptyxis` or, for a scheme with `ptyxis_light` under a light system colour scheme, `ptyxis_light`; `pty_mode`: `prefer-dark` dark, `prefer-light` light, `default` dark only when the GTK theme in use is a dark one, no gsettings dark), reads the key back (`Ptyxis palette key reads 'x'`) and warns when the id is not a built-in of the installed Ptyxis (`tools/ptyxis-ids.py ids`). GtkSource style schemes are installed like the palette (marker comment, same guard) into the user styles dir and the data dirs of installed Flatpak editors (they ignore host `~/.local/share`); `switch-theme` sets the `/org/gnome/TextEditor/style-scheme` dconf key (and Builder's only when it exists). Flatpak access is managed here too (`fp_*` in `tools/themectl.sh`): after `switch-theme` it offers (prompt, default no; no terminal: prints the command) the missing global read-only entries of one list, records only what it added in `$XDG_STATE_HOME/gnome-themes/flatpak-overrides`, and after the last theme and icon set (marker files) is removed it offers to undo exactly the recorded entries; never silent, no new recipe. `switch-theme` applies the accent (sed maps over the installed copies, remembered in `$XDG_STATE_HOME/gnome-themes/accents`), sets the GTK and Shell themes (dconf fallback when gsettings lacks the User Themes schema) and the libadwaita file `~/.config/gtk-4.0/gtk.css` (replaced silently only if generated by gnome-themes or a `.bak` exists, otherwise it asks).

## Workflow

CI (`.github/workflows/ci.yml`) triggers on push to `testing` (the quick run, the one the required checks come from) and on manual `workflow_dispatch` (input `full`, default true: the full suite; its concurrency group is separate, so a push does not cancel it); there is no schedule and there is NO `pull_request` trigger (a PR shows the push run's checks, `test` and `secrets` are required by name, verified through the branch-protection API 2026-11-09). Both jobs use the pinned runner `ubuntu-24.04` (a fixed image so a moving `-latest` cannot change results under us; the test job runs in `fedora:45` anyway) and checkout is pinned by commit SHA. The dnf install of the test packages takes about 90 s per run; a cached test image was not worth a registry push step.

`main` is protected: work goes to `testing`, CI (`.github/workflows/ci.yml`: job `test` runs `tools/test.sh` in a Fedora 45 container, job `secrets` runs gitleaks) must pass, and a pull request `testing` -> `main` is then merged (see README, Contributing). CI shellcheck runs at warning level.

## Reference moved from the README

The README is user-facing and short; these details live here.

- **Schemes and notes**: gruvbox-material, nordic, dracula, catppuccin, tokyo-night, solarized, everforest, fairy-floss, material, monokai, rose-pine, sweet, aubergine (Ubuntu terminal look). Dark-only: nordic, fairy-floss, monokai, sweet, aubergine. `fairy-floss` has no upstream licence (its colours are the Ptyxis "Fairy Floss Dark" built-in's, surfaces derived); `monokai` is classic Monokai, not Monokai Pro; light Gruvbox Material and Material have no built-in (`no_builtin`) and keep their own values. 
- **Shell calendar override**: the Shell themes are stock + colours + one marked block drawing the calendar flat (no circle per day, plain weekday headings, month label and arrows).
- **Accents**: one of the six terminal colours plus orange where the scheme has one (`<scheme>/accents/list`; not `rose-pine` and `fairy-floss`, whose upstream has no orange). Sed maps live in `accents/<accent>.{dark,light}.sed`; the chosen accent is remembered in `~/.local/state/gnome-themes/accents`. GTK 3 follows `gtk-application-prefer-dark-theme` in `~/.config/gtk-3.0/settings.ini`, not `color-scheme`.
- **Ptyxis**: every scheme uses a Ptyxis BUILT-IN palette, declared by ID. **Ptyxis keys the profile `palette` setting by palette id, not by display Name** (the resource file name without `.palette`, case-sensitive: `nord`, `dracula`, `solarized` are lower case, `Gruvbox Material`, `Rosé Pine`, `Catppuccin Mocha` are not; both `solarized` and `Solarized` exist and differ); an unknown value makes Ptyxis silently fall back to its default palette (the original bug: the tools listed and wrote Names). `tools/ptyxis-ids.py list|ids|show <id>` (wrapper `tools/ptyxis-palette.sh`) reads the ids from the binary (ELF section `.gresource.ptyxis` -> Gio.Resource); `PTYXIS_BIN` may be a directory of `<id>.palette` files (test fixtures). Declare `ptyxis = "<id>"`; a scheme whose dark and light built-ins are two flat palettes also gets `ptyxis_light = "<id>"` (Catppuccin Mocha/Latte, Tokyo Night/Tokyo Night Day, Rosé Pine/Rosé Pine Dawn); a sectioned built-in (nord, dracula, solarized, Everforest) covers both modes with `ptyxis` alone; where only the dark built-in exists (Gruvbox Material, Material) it serves both modes and `ptyxis_reason` says so. A light/dark pair cannot follow the system by itself (one palette key per profile), so `switch-theme` picks the id by the system colour scheme at switch time and says to run it again after changing light/dark. `ptyxis-compare.py --check` fails on a declared id that is not in the binary (and suggests the right-case id) and reports each scheme's delta E to its built-in as information. There are no generated palettes (a past experiment; `<scheme>/ptyxis/` is gone).
- **GtkSourceView**: installed into `~/.local/share/gtksourceview-5/styles` and, because Flatpak editors only read their own data dir, into `~/.var/app/org.gnome.TextEditor|org.gnome.Builder/data/gtksourceview-5/styles` when installed (no sandbox permission needed). `switch-theme` sets Text Editor's `style-scheme` (-dark while the desktop is dark, else -light) and Builder's only if present. Syntax colours are held at 4.5:1 on the editor background (comments 3:1) by changing lightness only; the generated file lists what moved.
- **Installer details**: install checklist defaults: themes start with every box off (an empty selection installs nothing, says so, exit 0; a named scheme skips the checklist); icons preselect the installed sets, else Papirus and Papirus-Dark. Checklist keys: SPACE, ENTER, q, up/down or j/k, a (all), n (none). `ICONS_URL` overrides the papirus source; icons use the XDG path (GTK also reads legacy `~/.icons`). Themes are real copies because Flatpak apps see `~/.themes`, not `/usr/share/themes`, and cannot follow symlinks. `update-theme` runs `git fetch` + `pull --ff-only` (quiet on a detached HEAD); icon clones under `~/.cache/gnome-themes/icons/<source>` are made or refreshed only for the sources of the sets being installed or updated (offline it uses the cache). Only each set's own folder is replaced. A same-named folder without the `.gnome-themes` marker is replaced or removed only after `y` (default no; no terminal: skipped with a message; `FORCE=1` overrides); folders from before the marker are adopted when their `index.theme` is identical. Tela and Fluent run their upstream `install.sh` (third-party code) into a temp dir. Icon sources: Papirus, Gruvbox Plus, Zafiro, candy, Tela, Fluent.
- **Flatpak access**: after `switch-theme`, if `flatpak` is installed and the global user override lacks any of `xdg-config/gtk-3.0:ro`, `xdg-config/gtk-4.0:ro`, `xdg-data/icons:ro`, `~/.themes:ro`, it asks once (default no); without a terminal it prints the exact `flatpak override --user --filesystem=...` command. Only missing entries are granted and recorded in `~/.local/state/gnome-themes/flatpak-overrides`; pre-existing entries are never recorded or removed. Removing the last theme and icon set asks (default no; no terminal: prints the `--nofilesystem` commands) to remove exactly the recorded entries.
- **New scheme**: `just new-scheme <dir> "<Ptyxis palette id>"` (see `tools/ptyxis-palette.sh list`), then `just generate <dir>`; checklist in `.claude/skills/build-scheme/SKILL.md`.
- **Requirements**: install needs `just`, bash and git; `just generate` needs python3, python3-gobject, GTK 3, GTK 4 and gnome-shell.
- **Testing and CI**: CI on the pull request is the test (job `test` runs `tools/test.sh` in a Fedora 45 container, job `secrets` runs gitleaks; both must pass to merge). Local tools (`tools/test.sh`, selftest, `ptyxis-compare.py --check`) are optional developer tools.
- **Licence**: tooling and docs MIT (`LICENSE`); generated theme files derive from stock GTK/GNOME Shell stylesheets and stay LGPL, each `*/themes/<Name>/` has its own `LICENSE`; `NOTICE` has the split and credits.

## Bulk schemes from the Ptyxis built-ins, CI sampling, featured themes

- **Inventory** `tools/ptyxis-schemes.tsv` (columns scheme, dark_id, light_id, status, reason, origin) is the source of truth for which Ptyxis built-ins became schemes: `existing` (the 13 hand-made schemes), `built`, `excluded` (with the reason: generic terminal preset, single-hue palette, light-only palette because the scheme format needs a dark variant, or the first failing check), `todo`. `python3 -I tools/bulk-scheme.py inventory|build [names] [--limit N]|status` (private recipe `bulk-scheme`). The builder runs `scheme-from-ptyxis.py`, resolves the TODO decisions with fixed defaults (derived orange, surface ladder, selection, comment and purple = magenta; no seventh accent; default_accent = the best contrast on bg_deep; credit and `ptyxis_reason` generated from the id and the origin URL in the built-in's header), then generate, selftest and `ptyxis-compare.py --check`; a scheme that fails any of them is deleted again and recorded as excluded. Pairs of one family (flat dark + flat light built-ins) are listed in PAIRS in the tool; a sectioned built-in is one scheme; other flavors are their own schemes. NOTICE carries one generic statement for these schemes plus the per-scheme `origin` column.
- **CI time and coverage** (`tools/test.sh`; measured on the 20-scheme run 42553407779, 4 vCPU: container + dnf 40-90 s, checkout+git ~15 s, fixed scenario tests ~60 s, selftest + regeneration about 10 s CPU per scheme (2.6 s wall with `xargs -P nproc`), the install/switch/update/remove loop about 3 s per scheme; about 6 s wall per scheme in all, so 166 schemes would cost ~16+ min, which is why a push does not run everything). **A push to `testing` runs the quick suite**: lint and hygiene for every scheme (LICENSE, headers, NOTICE coverage), inventory consistency, the scenario tests (collision guard, Shell theme, libadwaita file, Ptyxis ids, GtkSourceView, light-only, featured order, filter, icon recipes), `ptyxis-compare --check` (where a Ptyxis binary exists), the assets check, and for ONE set of schemes: regeneration, selftest and the install/switch/update/remove loop with every accent. That set is the featured schemes + the schemes changed against `origin/main` (`TEST_BASE` overrides; above 15 a deterministic hash sample of 15) + a rotating slice (`--sample N`, default 10) chosen by hashing the commit SHA, so every scheme is covered over time; the list and the reason are printed at the top of the log. Changes to tools/, justfile, assets/ or CI files do NOT escalate to every scheme. **The full suite** (every scheme: regeneration, selftest, loop with all accents) runs only on manual `workflow_dispatch` (`gh workflow run ci.yml --ref testing -f full=true`) and locally with `tools/test.sh --all`; it is not scheduled. A broken scheme that is neither changed nor sampled is therefore found only by a full run: dispatch one before a release or after generator or tool changes. Not done on purpose: matrix sharding, a cached test image (dnf is 40-90 s), a schedule; the shared assets are generated once per run (`GNOME_THEMES_SKIP_ASSETS`), not per scheme.
- **Featured themes**: `FEATURED_THEMES` at the top of the themes part of `tools/themectl.sh` (one line, order = display order; the environment variable overrides it, which the test uses; `tools/test.sh` reads the same line for the CI core). Featured schemes that exist come first in `list-themes` and every checklist, marked with a star, then all others alphabetically (C locale). The switch checklist only lists installed themes, so featured ones float there only when installed. Install checklists start with every box off.

- **Shared assets**: the stock PNG/SVG files the GTK stylesheets refer to as `url("assets/...")` are byte-identical for every scheme (no generator, engine or accent sed map ever touches them: the generators copy the library's resource bytes, `themectl` accent maps only run over the `.css` files), so the repo stores them once in `assets/gtk-3.0` and `assets/gtk-4.0` (written by `tools/assets-gen.py`, called by `just generate`; `--check` is part of CI) and `copy_folder` in `themectl.sh` copies them into each installed theme's `gtk-3.0/assets` and `gtk-4.0/assets` at install/update time, so installed themes are complete real directories (Flatpak cannot follow symlinks out of `~/.themes`). Per scheme this removes about 352 KB of content (308 small files, about 1.3 MB on disk by `du` because of 4 KB blocks). The theme folders' `LICENSE` (LGPL) is unchanged; `assets/LICENSE` carries the LGPL text for the shared copy. The selftest parses the CSS without the assets (GTK does not complain about missing url() files).
- **Light-only schemes**: a scheme.toml with a `[light]` table and no `[dark]` one (palette.toml says `light_only = true`): only `gtk-3.0/gtk.css` and `gtk-4.0/gtk.css` (GTK falls back to them when the desktop asks for dark), a `-Shell-Light` Shell theme only, a libadwaita file with the light values unconditionally (toast inverted), only `accents/<a>.light.sed` (the `accents/list` has the light hex in the first colour column and `-` in the second), only the `-light` GtkSourceView id. `switch-theme` picks the Light Shell theme and the `-light` id whatever the desktop mode is. The libadwaita accent maps apply the light map before the `@media (prefers-color-scheme: dark)` line and the dark map after it, because schemes can share a hex between variants (`accent-maps-gen.py` verifies exactly that).
- **Checklist pickers** (one place: `choose_many` for install/remove, `choose_one` for switch, themes and icons; the accent submenu of `switch-theme` always uses the built-in). Handler: `THEMES_PICKER=fzf|gum|builtin` forces one (fzf/gum missing: a warning and the built-in); unset: `fzf` when it is on PATH and there is a terminal (`--multi --layout=reverse --height=~70%`, entries `<index>TAB<label>` with `--with-nth=2..`, items start unmarked except the icon preselection, featured first with the star, TAB marks, ENTER confirms the marked ones (fzf >= 0.45: ENTER with nothing marked aborts instead of taking the highlighted one), fzf's own fuzzy filter replaces `/`; Esc/Ctrl-C = "Cancelled."), else the built-in picker, and without a terminal the numbered list. gum is only used when forced (`gum filter --no-limit` / `--limit 1`); the base image has fzf, not gum, and this repo must not depend on ublue's `ugum`. Named schemes skip the picker. Chosen entries map back by index (a handler that returns only labels is matched by name with the star and the description stripped). Tests use stub `fzf`/`gum` binaries (`FZF_STUB_*`, `GUM_STUB_*` in `tools/test.sh`); the test suite sets `THEMES_PICKER=builtin` by default.
- **Built-in picker viewport rule**: the frame is 1 header line + H list lines + 1 footer line, H = terminal rows - 2 (at least 1, at most the number of entries); `top` is the first shown row of the (filtered) list and only moves by the minimum needed to keep the cursor row visible (so one cursor step moves the window by at most one row; wrapping from the first to the last entry jumps); the footer shows `first-last of total`, the filter and the tick count; every line is cut to the terminal width, the frame is redrawn in place (cursor up H+1, clear to end of line) and the cursor rests on the footer row so a full-height frame never scrolls the terminal; a size change (polled every 0.3 s in `_tui_wait_key`, `read` is not interrupted by SIGWINCH) clears the screen and redraws from the top. Root cause of the old bug: the picker printed ALL entries and moved the cursor up n+1 lines, which cannot reach beyond the screen top when the list is taller than the terminal, so every redraw scrolled the terminal and the view stuck at the bottom. Keys: up/down j/k, PgUp/PgDn, Home/End or g/G, SPACE, a/n (shown entries), `/` filter (substring, case-insensitive, Enter keeps, Esc clears; ticks survive), ENTER, q. `tools/pty-scroll-test.py` runs the picker in a pty with a small terminal emulator (10 and 24 rows, 187 entries) and asserts after every key: one highlighted row with the expected entry, header and footer on screen, window top moved by at most one; plus last/first, pages, a filter, off-screen ticks and resizes. It runs in the quick suite.
- **Dev gotcha**: any `themectl.sh` experiment must set `THEMES_DEST`, `GTKSOURCEVIEW_STYLES`, `FLATPAK_APPS`, `PTYXIS_PALETTES`, `XDG_STATE_HOME`, `XDG_CONFIG_HOME`, `GNOME_THEMES_CACHE` to temp dirs: `install-theme` also writes GtkSource style schemes into `~/.local/share` and the Flatpak editors' data dirs.

## Scope and delegation

- This repo is its own Claude project: work only inside it. Never edit anything outside it (other repos, the real themes or icons directories, home-directory configs, live gsettings/dconf). Tests use temp dirs and `THEMES_DEST` / `ICONS_DEST`, as `tools/test.sh` does when it is used.
- Anything that needs the outside (applying a theme on the desktop, a live check in the running Shell, a change in another repo) is not done here. Report it as a request under `Needs from hub:` to whoever spawned the session, who handles or delegates it.
- Work on this repo from other sessions goes through a project agent spawned by that hub, not through direct edits to these files.
